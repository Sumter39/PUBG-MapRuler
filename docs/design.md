# 技术设计

## 架构

单进程，两个原生窗口 + 一个 Tk 面板：

```
src/main.py     单入口：Win32 宿主（托盘/热键/消息循环）+ 控制面板 + 点位投影层 + 识别
src/dxgigrab.py DXGI 桌面复制抓屏（HDR 屏颜色正确），GDI ImageGrab 兜底
src/app.manifest  PerMonitorV2 DPI 感知声明
build.py        PyInstaller 打包：assets/ 与 data/ 随包，通过 sys._MEIPASS 读取
```

## 点位投影

完整地图（按 M 打开）是屏幕正中、边长等于屏高的正方形，纯固定公式对齐，
不识别、不抓屏：

```
side = H    left = (W − H)/2    top = 0    1 km 网格 = H/8
x = (lng+180)/360 × side        y = (lat+90)/180 × side
```

该矩形来自旧 EXE 逆向取证：基准图 9 条竖网格线精确落在 `x = 560 + k·180`
（2560×1440），反汇编确认识别仅用于跟踪放大/平移，基础矩形固定。
换分辨率时矩形随 H 自动缩放，无需配置。放大/平移后的测距识别按网格
实时重测比例尺。

## 测距识别链路

```
抓帧（DXGI 桌面复制优先；抓屏前把自己的图层 alpha 归零，帧内只剩游戏）
→ HSV 色相掩膜（每队一个色相窗口；色相对亮度拉伸/削顶不敏感）
→ 环形度整图扫描出候选（四象限均衡，挡直边/大色块）
→ 窗口精修环打分（这一步即「阈值化挑点」，只留队伍色圆环）
→ 串链：逐对判定两点之间**是否真有一条完整的线**（见下）
→ 共线判定：直线量距离；折线认出但距离留空

### 抓屏：HDR 桌面上必须显式索取 FP16（v4.0.10）

**现象**：同一张图，主屏（HDR 屏）抓出来比肉眼亮得多、亮部糊成一片；副屏
（非 HDR）完全正常；连 Windows 自带截图工具在主屏上也一样过曝。

**根因（灰阶对照实验，不是推测）**：画一组已知灰阶窗口，只切显示器的
HDR 开关，回读抓屏值：

| 绘制值 | HDR 关 | HDR 开 |
| --- | --- | --- |
| 16 | 16 | 33 |
| 32 | 32 | 59 |
| 64 | 64 | 109 |
| 96 | 96 | 160 |
| 128 | 128 | **210** |
| 160 / 192 / 224 / 240 | 原值 | **全部 255** |

HDR 关闭时**逐档精确无损**；HDR 一开，8 位复制链立刻套一条提亮曲线并把
160 以上全压成纯白。UI 采样同向印证：左侧栏 (22,27,28) → (46,54,57)，
近乎恒定的 ×2 增益。所以这**不是**我们的转换算错（HDR 关时 0/17 档误差），
是这条 8 位通路本身装不下 HDR 桌面的内容——所有走它的截图工具都会过曝。

**修法**：用 `IDXGIOutput5::DuplicateOutput1` 在格式列表里显式写
`R16G16B16A16_FLOAT`，直接拿 scRGB 原始值，不再经过那条 8 位降级。

两个本机特有的坑：

1. **`QueryInterface(IDXGIOutput5)` 返回 `E_NOINTERFACE`**（Output3/4/5/6
   全部如此，而 `IDXGIFactory6`、`IDXGIAdapter4` 又是可用的），所以按文档
   拿不到接口指针。实测该对象**确实实现**了这个方法，只是不响应 QI——
   只能按槽位直调，槽位 26（`DuplicateOutput=22` 之后依次
   GetDisplayModeList1/FindClosestMatchingMode1/GetDisplaySurfaceData1、
   SupportsOverlays、CheckOverlaySupport、CheckOverlayColorSpaceSupport）。
2. 直调有风险，所以 `_vt_slot_ok()` 先确认该槽位的函数指针落在
   `dxgi.dll` 映像范围内，不在就退回老接口，避免在缺该接口的系统上跳到
   随机地址把进程打崩。

现在的策略：

| 情况 | 处理 |
| --- | --- |
| `DuplicateOutput1` 可用 | 请求 `[FP16, BGRA8]`，HDR 桌面直接给 FP16 |
| 拿不到 / 老系统 | 退回 `DuplicateOutput`（非 HDR 桌面够用） |
| 帧格式 FP16（10） | 采用，交 `_tonemap_fp16` |
| 帧格式 SDR（87） | 记作兜底，继续找 FP16；最多 6 帧 |
| 全黑帧 | 丢弃继续（`_frame_black`：FP16 查 RGB 6 字节，SDR 查 3 字节） |

**`_tonemap_fp16` 的软肩**：scRGB 1.0 = 80 nit，正常内容在 0~3.0
（SDR 白 = 240 nit）。但游戏逆光/太阳实测能到 **12.9（≈1030 nit）**，
直接 `clip(v/3.0)` 会把门口整片压成纯白（实测 51.4% 撞顶、区域里只剩 1 个
色值）。改成：

```
x = v / 3.0
x ≤ 0.75        线性不变（地图界面、UI 一个像素都不动）
x > 0.75        0.75 + 0.25·(1 − e^(−(x−0.75)/1.5))   单调、渐近 1.0
再统一做 gamma 2.2
```

同一画面效果：门口削顶 51.4% → **1.6%**，区域色阶从 1 级 → **252 级**，
p50 255 → 224。地图界面因为落在 `x ≤ 0.75` 内，不受影响。

代价：FP16 帧要多读一倍字节；识别是手动触发，可以接受。

### 抓图范围：整屏（v4.0.12）

旧版只抓「屏幕中央、边长 = 屏高×scale」的方块。地图放大铺满整屏后，伸到
方块两侧的轨迹端点会被裁掉：实测 zoom16 那条青线左端点正好压在 x=0，只剩
74px，`_ring_scan_np` 的四象限判据直接否掉 → 只剩一个端点 → 「无轨迹」。
现在 `_map_box_phys()` 直接返回整屏物理框，`_grab_map()` 不再 resize 成
side×side，`TrackProbe` 吃完整矩形。

**`side` 不跟着改成屏宽 2560**：它是比例尺基准
（`zoom = 大格像素 ÷ (side/km)`），完整地图的方块边长仍是屏高，所以
`side = H × scale` 保持不变，否则同一条线会从 zoom 8 变成 zoom 45。
网格识别的 `_canvas` 从整屏**居中**取 `min(W,H)` 方块（正方形帧 cx=cy=0，
与旧版逐像素等价），所以量测不受抓图宽度影响。

整屏带来的额外开销用两处**纯性能**优化抵消，识别结果不变：

| 优化 | 收益 |
| --- | --- |
| 4 队共用一次 HSV 转换 | 1.26s → 0.31s |
| 环扫描只在掩膜像素的包围盒内做 | 2.35s → 约 0.6s |

实测：整屏 2560×1440 FP16 抓图约 1.06s，网格 + 轨迹合计约 2.5s，与旧
方块版总体相当。离线模拟（把 1440² 测试帧贴到整屏中央）四张帧的网格结果
与距离与方块帧逐帧一致；回归 13/13。

「是否有连线」按本质到辅助分五层，不看两点是否共线、也不看全局平均命中率。
采样用**法向 ±3px 窄带**（沿线路横截面只查 7 个像素），不是 7×7 方块——
方块等于允许采样点偏离 3px 还命中，旁边的地形像素会被算成线。

| 层 | 阈值 | 真链实测 | 假边实测 | 挡住什么 |
| --- | --- | --- | --- | --- |
| ① 端点出线 | ≥0.70 | ≥0.91 | 0.18~0.55 | 孤立人物编号标记；±30° 取最佳方向，兼容折线拐点 |
| ② 全局覆盖 | ≥0.85 | ≥0.95 | 0.65（伪直连） | 允许 15% 缺失，不要求 100% |
| ③ 最长连续缺口 | ≤12 px | ≤5 px | 10~435 px | 「零散小缝」与「线整段断了」的分界 |
| ④ 分段连续 | 每段 ≥0.65 | ≥0.77 | 0.28 | 假点共线、后 2/3 压在真线上 |
| ⑤ 细描边 | far_ok ≥0.72 | ≥0.79 | 0.65 | 区域色块边界（蓝圈弧线、麦田） |

几条实测依据：

- **方块口径**下伪直连的覆盖是 0.89，正好撞上「89% 有连线的真线」，单靠全局阈值分不开；
  改窄带后同一帧真线 0.981→0.952、伪直连 0.894→0.648。也就是说 0.89 不是「真有线」，
  是 7×7 方块把旁边的真线和地形一起算进来了。
- 用真实橙线模拟 11% 像素缺失：分散缺失 → cover 0.885 / 单段 0.706 / 缺口 7.5 px → 通过；
  同样 11% 集中成一段 → 单段 0.0 / 缺口 55 px → 否决。所以高阈值放全局（0.85），
  局部留余量（0.65），靠 ③ 区分缺失是分散还是断档。
- **地形色确实更浅**：伪直连的 A 段（麦田）命中像素 S 中位 52%（133/255），V 中位 92%；
  真线 S 中位 71%（181/255）、V 100%。但 line 掩膜的 S 门槛不能直接抬到 140 ——
  绿色线的半透明混色 S 只有 135~144，抬上去会丢 4 条已验证绿线（回归 20 帧从 21 条掉到 14 条）。
  地形色靠**窄带 + 覆盖门槛**挡住，比调 S 安全。

人物点与轨迹点**不按圆环形态硬分类**——实机里画线端点也可能是带白色数字的实心标记（231937 帧橙线两端就是），按内核暗度筛点会把真轨迹删掉；区别只能由线本身给出。
```

- 颜色分类用 **HSV 色相窗口**：屏幕标记色随曝光/削顶/背景混合漂移
  （蓝→纯青、黄→削顶纯黄），固定 RGB 阈值不可靠，色相一个区间覆盖全部变体。
- 比例尺来自游戏自带网格：1 km 黑粗线 + 100 m 白细线，剖面找峰 + 间距投票
  + 最小二乘精修；置信不足回退 `kmSize × 1000 / side`（结果标「估算」）。
- 队伍颜色以**实机截图取样**为准（Normal 色盲模式）：1 黄 `#FFD700` /
  2 橙 `#FF9643` / 3 青 `#00DCDC` / 4 绿 `#3CE070`。旧版取
  `UiHelperFunctionsBp.GetTeamColor` 的蓝图线性色常量直接 ×255，未做 sRGB
  编码，得到「2 红 / 3 深蓝」，与屏幕像素差一个色系；由此划出的 HSV 窗口
  把 2 号橙全归到 1 号黄槽。v4.0.1 起识别窗口与面板色同源，分界 H(PIL)=30。
- 只提高全局 `far_ok` 门槛是治标：伪直连曾以 0.646 突破旧门槛 0.62，
  把同一条轨迹从 359 m 拉成 490 m。根因是「两点之间是否整条有线」
  从未逐段验证，v4.0.2 的分段连续性是针对性修复，v4.0.3 再补上全局
  覆盖率与最长连续缺口两道阈值，避免「只卡一个数字」误杀局部遮挡的真线。

## 比例尺识别（网格）

```
抓帧 → 去掉边缘罗盘/队友栏 → 蓝通道(B) + 亮度(L) 各出两条剖面（按列/按行取均值）
→ 减去 41px 局部均值（暗线为负、亮线为正，抵消大片地形明暗）
→ 找峰（认平台取中点）→ 峰间距投票 + **内点重拟合**（v4.0.7）
→ 按**占位率**评分，通过直线校验的候选里取**最小基本周期**
→ 大格/小格互证（1 km = 10×100 m，只检到隔一条时按 20/5 倍校正）
→ 直线校验：候选周期必须落在一组**横平竖直、贯穿地图**的直线上
→ 全流程失败 → 用**去过曝副本**重跑一次（v4.0.7 兜底）
→ 置信 < 0.12 或校验不过 → 判「无网格」，不给距离
```

### 三个坑（都是实机帧逼出来的）

**① 噪声峰把真周期否掉。** 剖面里真线只有 4 根，地形噪声峰十几根，旧版把
两者平等喂进最小二乘：rms 被拉到 40+、内点率掉到 0.2，真周期直接被否。
实机帧里 114/402/690/978 四条真线精确 288 间距（峰值 13~28），却判「无网格」。
现在先按粗周期算 `k = round((x−a)/p)`，只留残差 ≤2.2 px 的内点重拟合，
判据也只看内点。

**② 公约数抢走基本周期。** 288 的点阵对 96 也成立（288 = 3×96），旧版取
「升序第一个能拟合的」就会锁到 96，比例尺直接错 3 倍。改成算**占位率**
（落在点阵上的峰数 / 这段跨度里该有的位置数）：真周期 ≈1.0，公约数只有
0.3~0.5。反过来 144 与 288 都可能是真周期，就取「占位率 ≥0.8 且内点 ≥4
的候选里最小的那个」——144 少认一根线时仍以 0.89 胜出，288 是真周期时
144 的点阵会空一半位置，进不了这一组。

**③ 抓帧过曝（v4.0.8：改在抓图时解决）。** 桌面复制拿到的帧常年大片削顶
（实机 01:55 帧 **24%** 的像素三通道全 ≥245），网格白线和浅色地形被压成
同一片白。抓图函数 `_grab_map` 现在**在保存之前**判断削顶比例：≥10% 就按
亮度分位（1%~99%）把整幅拉到全程，三通道共用同一条 LUT（增益/偏移一致），
所以不会偏色、队伍标记的橙青黄不会互相串。

- 落盘的截图、面板预览 = 拉伸后的图，肉眼看到的就是正常的；
- **识别仍然吃原始帧**（`self._raw_frame`）：颜色阈值是按原始像素标定的，
  不该跟着截图增强一起变。`_scan` 里 `ana = self._raw_frame or im`。

削顶不可逆：已经压成 255 的像素回不来，拉伸只把被蒙层挤扁的中间调拉回量程。
实测 01:55 帧 79~255 → 0~255，同一帧的网格从「无网格」变回 288 px（100 m）。

识别侧另有一条独立兜底（与截图无关）：常规探测失败时，用「软肩 + gamma」
的高光压缩副本再试一次——450 m 那帧（浅色地形上的白线）压完高光反而更弱，
所以它只能当兜底，不能进主链路。

### 直线校验（`_verify`）

剖面法把二维压成一维，**任何有重复感的地形纹理都能凑出周期**（实测赛前帧
锁到 13.09 px 当成 100 m 格）。而网格线的本质是**直**：竖线在整列上同色、
横线在整行上同色、贯穿整张地图，地形条纹做不到「同一条像素列上一条接一条」。

| 步骤 | 做法 |
| --- | --- |
| 细线响应 | 本像素减（左右各 4 px 均值）→ 亮线为正、暗线为负，宽色块与缓变地形被压掉 |
| 二值化 | 响应 ≥ 5 记为「有线」（v4.0.13，原为 12，理由见下） |
| 贯穿率 | 按列（或按行）求平均 → 每条候选线上取 ±1 px 内最大，再对整周期找最佳相位、取所有线的平均 |
| 门槛 | ≥ 0.55 |

实测 20 张留帧 + 4 张赛前帧：真网格 **0.67~0.97**（最差是 450 m 那帧的浅色地形），
假周期 **0.16~0.41**。两侧都留了余量，不是卡着某一张图调出来的数。

**v4.0.13：二值化阈值 12 → 5**（放大后格子线落在海洋/浅色地形上会被漏）。
实机 173552 帧：192 px 真格子线的响应只有 5~10，阈值 12 把整列贯穿率压到
**0.488**（不过 0.55）→ 误判「无网格」。而同一帧按 384 px（2 倍）扫却有
0.856，很容易误导成「格子放大了」——但格子是游戏按世界坐标画的固定网格，
同一缩放档下不可能一会儿 192 一会儿 384。降到 5 后的对照：

| 周期 | 阈值 12 | 阈值 5 |
| --- | --- | --- |
| 192（真，173552） | 0.488 ✗ | **0.631** ✓ |
| 192（真，173356） | 0.731 | 0.934 |
| 13 / 17（地形假周期） | 0.11 | 0.31（仍 far below 0.55）|

降阈值同时抬高真、假周期，但真周期抬得更多，0.55 门槛两侧仍有余量；
13 例回归全过、真实周期回到 192（zoom 10.68，与此前成功帧的 10.67 一致）。

校验不过时**不给值**：面板显示「无网格」。宁可承认量不到，也不给一个能算出
离谱距离的比例尺——比例尺错 10 倍时，轨迹本身认得再准也没意义。

### 缩放是连续的，没有「档位表」

曾经花很大力气去逆向 PUBG 的滚轮档位，结论是**这东西不存在**，别再找了。

证据一（静态）：`NewWorldMapWidget_BP` 的 CDO 只有 `ShowGridZoomLevel = 25.0`
和 `TacticalWheelResponseTimeSeconds = 0.15`；配置项 `WorldMapZoomSpeedLevel`
是 0~10 的**速度滑条**，不是档位选择器。0.15 s 插值本身说明缩放量是连续逼近的。

证据二（测量）：6 个不同缩放的实机帧，`px/100m ÷ zoom` 全部落在 180.0
（偏差 ≤0.14%）：

| 帧 | zoom | px/100m | 比值 |
| --- | --- | --- | --- |
| zoom4_orange_line | 4.01 | 720.8 | 179.8 |
| zoom8_*（7 张） | 8.00 | 1440.0 | 180.0 |
| zoom16_deka | 16.0 | 2880.0 | 180.0 |
| zoom21_cyan_line | 21.31 | 3835.0 | 180.0 |
| zoom24_prematch | 24.0 | 4320.0 | 180.0 |
| zoom32_line_offscreen | 32.0 | 5760.0 | 180.0 |

180 不是巧合，就是 `base = side / km = 1440 / 8`。也就是说
`px/100m = (side / km_size) × zoom`，而 `zoom = (100 m 格像素 × 10) / base`
——**同一件事的两种写法**。所以「拿 zoom 去校验 px/100m」是循环论证，没有校验力。

推论：

- 21.31 / 24 这两个中间值是滚轮停在半途的正常状态，**不是量错**。旧结论
  「3835、4320 不在 2^k 网格上 → 量错」作废。
- 不要做「偏离合法档位 >6% 就判可疑」的白名单，没有合法档位可依。
- 真正能挡住比例尺量错的是**多尺度互证**：1 km 大格与 100 m 小格必须成
  7.5~13 倍关系（`probe` 里已经在用），以及 `_verify` 的直线贯穿率。

### 网格线颜色实测：不能用颜色建轴（负结论）

`MapGridWidget` 的 CDO 静态解出来是：

```
ColorSmallGrid              = RGB(0.887, 0.887, 0.887)  A=1.00   中性灰白
ColorLargeGrid              = RGB(0.034, 0.034, 0.122)  A=0.75   近黑蓝
DefaultThicknessMultiplier  = 1.0
MinThicknessMultiplier      = 0.25
```

看着像是「两条颜色轴可以分别做阈值」，实测下来**不成立**，别再做。

**① 线上像素的颜色随地形漂移，固定色匹配会失效。** 取细线响应最强的列，
读线上像素中位数：

| 帧 | 地形 | 亮线实测 | 暗线实测 |
| --- | --- | --- | --- |
| zoom8_orange_line | 绿草地 | `#A4A187` | `#70735B` |
| zoom16_deka | 雪地/冷色 | `#E4EDFF` | `#8293DF` |
| zoom24_prematch | 沙漠 | `#FFF9D8` | `#E2CCAD` |
| zoom8_prematch_cyan | 米黄 | `#FBECD2` | `#D7C7AD` |

离 `#E2E2E2` 的距离从 31 到 133，差 4 倍。所以「到固定色的距离」没有统一阈值。

**② 线的增量方向是中性，颜色本身不带信息。** 逐像素算「线像素 − 左右各 4 px
均值」（取最极端的 0.1%，避免被地形稀释），归一化后：

| 帧 | 亮线 Δ | 暗线 Δ |
| --- | --- | --- |
| zoom8_orange_line | (+0.91, +0.91, +1.00) | (−1.00, −0.99, −0.97) |
| zoom4_orange_line | (+0.95, +0.93, +1.00) | (−1.00, −0.96, −0.99) |
| zoom16_deka | (+1.00, +0.99, +0.86) | (−1.00, −0.99, −0.79) |
| zoom24_prematch | (+0.75, +0.84, +1.00) | (−0.97, −1.00, −0.98) |

三通道同向等幅，极差只占幅度 3%~9%。线只是把局部地形整体抬亮/压暗，
**几乎不改色相**（半透明叠加 + 色调映射的结果）。所以「按线色匹配」拿不到
比亮度更多的信息。

**③ 换成「中性度」剖面能提 conf，但会换答案。**

试过把亮度剖面改成 `亮度 − K·(max−min)`（K 越大越压彩色地形）：

| K | 12 例错 | 32 张历史帧漂移 | 典型 conf 变化 |
| --- | --- | --- | --- |
| 0（现状） | 0 | 0 | zoom8_yellow 0.50 |
| 0.6 | 0 | 1 | 0.66 |
| 1.0 | 0 | 1 | 0.74 |
| 1.4 | 0 | 0 | 0.87 |
| 1.5 | — | 0 | — |
| 1.6 | 1 | 2 | 开始把 432 判成 288 |
| 2.0 | 3 | 9 | 崩 |

conf 确实涨了 20%~80%，但 K 的有效窗口只有 0~1.5，K=1.6 就翻车；而且
K=0.5~1.0 时 `scan-20261116-014227` 从 288 跳到 432（1.5 倍，不可能是网格
周期的整数倍，是错的）。**conf 不是瓶颈**（最低的帧也有 0.18，远高于 0.12
的采纳门槛），所以这点提升换不来任何东西，只有风险。

**④ 把中性度用作 `_verify` 的闸门同样不行。** 三通道取「共同同向分量」后：

| 帧 | 周期 | 亮度响应 | 中性响应 |
| --- | --- | --- | --- |
| 014227 | 真 288 | 0.88 | **0.55**（勉强过线） |
| 014227 | 错 432 | 0.71 | 0.40（挡住了 ✓） |
| zoom24_prematch | 真 432 | 0.56 | **0.35**（掉到 0.55 以下 ✗） |
| zoom16_deka | 真 288 | 0.65 | **0.31** ✗ |

错误候选确实被压下去了，但**真周期被压得更狠**，净效果是判别力下降。

结论：网格线颜色/中性度这条路到这里为止，保持现有 `B 通道 + 亮度` 双剖面。
如果以后要降误判，方向应该是**时序一致性**（同一缩放下连续几帧的结果应当
稳定），不是颜色。

## 测试集与回归

识别链路改一次就可能动到别处（颜色分带、环打分、连线门槛互相牵连），
所以固定一套**差异化样本**做回归，每次改完必须跑。

### 什么图进测试集

只收**有差异**的样本，同质的重复帧不收：

| 类型 | 例子 |
| --- | --- |
| 同一轨迹的不同缩放档 | 同一条橙线 zoom 4 与 zoom 8（锁定「跨档距离必须一致」） |
| 不同队伍色 | 黄 / 橙 / 青 / 绿各一条，防止再次出现「2 号橙落进 1 号槽」 |
| 难样本 | 标记叠合、被地形或 UI 遮挡、深度放大（zoom 32）、满图（zoom 1） |
| 过曝样本 | 削顶 20%+ 的帧（赛前蒙层、Deka M 加载图），锁「压高光后仍能量到比例尺」 |
| 反例样本 | 本来就量不到的帧（线一端在屏幕外），期望「无轨迹」，防止程序硬凑出一个值 |
| 回归样本 | 曾经误判/漏测的帧，修好后必须留一张，防止回退 |
| 用户提供的样本 | 用户实机截图优先收，它代表真实分辨率与画质 |

### 收录规则

1. 图片放进 `testset/frames/`，同时写 `testset/expected.json`。
2. 期望值必须**人工确认**（看图核对）或与历史 `scan.log` 核对，
   **不能直接拿当前程序输出当答案** —— 那样永远 100%，测不出回归。
3. 槽位（队号）必须精确，距离允许 ±2%（`tolerance`），zoom 允许 ±5%。
4. 反例用 `"grid": "none"` 标注：该帧没有网格，比例尺必须回退成「估算」，
   距离必须为空。**「不测」也是正确答案**，比测个错值好。
   只校验比例尺、暂不校验距离的用例写 `"check": "grid"`（例：过曝帧能认出
   网格但轨迹距离还没人工确认）。
5. 改识别链路的任何一处（`_HSV_BANDS` / `marks` / `_linked` / `_verify` / 网格）
   之后跑 `python tools/testset_eval.py`，**全部通过才算做完**；
   失败要先证明是代码错还是期望值错，改完再提交。
6. `testset/` 被 Git 忽略（本机截图，含玩家名等信息）；脚本与本节入库，
   换机器时按本节的规则重建测试集。

### 识别算法大重构的尝试与结论（v4.0.15，勿重复踩坑）

针对「阈值串联、识别率低」，试过两条重构路线，**均未达到 19/19，已回退**。
结论与实测数据留档，避免以后重复投入：

- **路线 A：彩色 ZNCC 模板匹配**（`track_template.py`，已删）。
  从真实帧抠 27×27 环模板、屏蔽中心数字做归一化互相关，颜色另判。
  **否决原因**：单模板覆盖不了同队不同端点——从端点①抠的模板去匹配
  端点②只有 -0.15~0.51（同一标记受数字、连线方向、地形叠加影响，像素
  外观差异极大）。全测试集只有 9/19。程序生成「理想圆环」模板更是全部
  匹配不上（真实标记有抗锯齿/色调映射）。
- **路线 B：白色数字定位 + 颜色聚类**（`track_digit.py`，已删）。
  白色数字是 UI 叠加、不受曝光漂移，16 个标记定位全中（中心偏移<1.5px）；
  环带色相聚到 4 类。**否决原因**：同队色相漂移比类间距离还大——`zoom21`
  同一条青线两端色相 85 和 30，`zoom16_border` 青端点 129，K-means 把同队
  拆散。全测试集 14/19：修好了 3 个 HDR 难样本，但破坏了贴边/淡线/赛前
  蒙层 4 个老样本，净收益为负。

**为什么旧算法虽"丑"但更难替代**：它把「颜色掩膜」用在**定位**这一步，
恰好给连线判定提供了干净的点集——假点被颜色先滤掉了。新方案用数字定位
虽稳，但把大量地形白点放进候选集，`_linked` 反而连不上真线。颜色聚类试图
补这个洞，但 HDR 下同队色相跨度超过类间距，补不住。

**真正的出路（若要再重构）**：不能用任何单一绝对阈值（颜色/色相/亮度），
必须是「数字定位 + 连线拓扑分组为主，颜色只做链级多数投票」——先靠线把
点串成链（链天然同队），再用链上多点颜色投票定队伍（容忍单点漂移）。
路线 B 只做到「先聚类再连线」，顺序反了。这是一个完整工程，不是调参，
需要单独安排时间，且必须保住现有 19/19 回归。

### 用户指出的关键形态事实（重要，后续重构以此为基础）

用户逐帧指认，看图确认属实：

1. **数字 = 队伍号，是定死的分类标准**：终点标记里的白色字符 1/2/3/4
   就是队伍 1/2/3/4。之前误以为"数字是标记序号"，是因为把 V 形箭头
   误读成了数字（`zoom8_yellow_line` 一端是"1"、另一端是箭头，不是"2"）。
2. **箭头 = 起点 + 指向连线方向**：起点标记里是白色 V 形箭头「>」，箭头
   尖端精确指向下一段线的延伸方向（看图逐帧确认，误差 0°）。箭头是纯白
   UI + 几何形状，不受颜色/曝光/地形影响。
3. **人物标记也有数字但没有连线穿出**：靠"是否有连线"做形态学验证区分。

**据此实现的 v6 原型（已验证核心信号，未达 19/19，已回退）**：
- 深色圆盘 (14×14) 找所有节点：10/10 命中，含 HDR 帧
- V 形箭头 8 方向模板匹配判向：iou 0.69~1.0，判向误差 **0°**
  （用质心/最远白像素判向会错——V 形质心在两条尾巴侧，不在尖端，见讨论中的图）
- 数字 1/2/3/4 模板匹配定队伍：干净样本 5/5 正确
- 沿箭头方向成链：链端点坐标精确
- 单帧抽检 5/5 全对（含 zoom42/weak 等 HDR 难样本）

**但全 18 帧回归只有 12/19**：`zoom4_orange`（放大档数字变形认错队）、
`stacked_marker`/`prematch`/`border`（箭头或数字模板没覆盖到的变体）、
`polyline`/`deka`（链只连了部分节点）。根因是**模板样本太少**——箭头和数字
都是从 3~4 张帧抠的，没覆盖所有缩放档/叠加变体。要继续这条路线，必须
**系统采集全 18 帧的箭头/数字样本建多模板库**，而不是从 4 张帧外推。

**结论**：v6 的信号选择（圆盘 + 箭头方向 + 数字定队伍）是对的，比 v5 的
颜色聚类稳得多；差在模板覆盖度。这是一条值得继续的路，但需要专门一轮
做样本库，且必须保住 19/19 基线。今晚未接入，main.py 保持 v4.0.15。

## 窗口与输入

- **面板几何由 Win32 全权接管**：尺寸位置只走 `SetWindowPos`，Tk 不参与
  布局传播（`pack_propagate(False)`）；子类化窗口过程吞掉 `WM_DPICHANGED`，
  混合 DPI（如主屏 125% / 副屏 150%）下面板物理像素 1:1，跨屏不重排不模糊。
- **分层窗口收不到键盘焦点**：`overrideredirect` 透明面板上 Tk 的
  `focus_force()` + `bind_all("<KeyPress>")` 永远等不到按键。热键捕获因此用
  `GetAsyncKeyState` 轮询 + 自维护状态表做按下沿检测，与焦点无关；录制期间
  先注销旧热键，提交/取消后恢复。
- 显隐热键用 `RegisterHotKey`，触发时以 `GetAsyncKeyState` 查物理按键区分
  左右边；运行时改绑走自定义消息 `WM_REBIND`。
