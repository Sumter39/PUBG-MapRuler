## 1. 箭头识别：几何法优于小模板匹配

**背景**：PUBG 地图路线标记里的白色 V 形箭头（chevron）需要识别指向。早期用
pak 解码贴图做模板旋转匹配（8px 屏幕尺度下），区分度极差；后改为实机屏幕模板 +
NCC 仍不够稳。用户指出箭头形状固定且**轴对称**，几何量比小模板精确。

**触发场景**：需要识别小尺寸（20~34px）白色 chevron 的 360° 任意指向时。

**结论**：纯几何法三步——
1. **对称轴扫描**（mod 180°，粗扫 2° + 细化 1°）：像素投影到轴坐标系，
   镜像点在容差 1.35px 内有像素则命中，命中比例即对称分；
2. **指向裁决**：轴本身无指向，利用对称形状两端散布差异——尖端沿轴收成
   一点（垂向散布小）、尾部是两条臂（散布大），散布比 ≥1.18 的一端即指向；
3. **尺寸门 20~34px**：真 chevron 是固定屏幕尺寸 UI（18 个实测样本全部
   22~34px），大号数字字形（37~90px）和碎块（≤19px）两端堵死。

**适用边界**：适用于固定屏幕尺寸的白色 chevron 类 UI。注意单独的对称分
区分度近零（见第 9 条），必须与散布对比、尺寸门组合使用；纯几何结论
（散布比、尺寸区间）是按本机分辨率（2560×1440）实测的，换分辨率需重标定。

## 2. 箭头单向指向：只指下一个环，链首可以无箭头

**背景**：成链校验一度按 ±180° 双向容差匹配箭头，导致反向假链。

**触发场景**：用箭头方向约束链的走向时。

**结论**：标记环上的箭头**只单向指向下一个环**（它不知道上一个环在哪），
方向校验只做正向锥（±25°）。但有一个实测例外：**玩家位置大盘（链首）
本身没有箭头**——线直接从大盘连到下一个标记。所以 DFS 第一步允许走
无箭头邻接边，但起点必须持有强数字身份（NCC≥0.70），防止污染块起假链；
后续每步仍要求箭头指向。

**适用边界**：适用于本游戏标记体系。放开无箭头起点后，同一几何路径会
双向成链，必须配链级方向仲裁（见第 7 条），否则反向假链反超真链。

## 3. 环内白色内容的硬约束：圆形掩膜 + 最近块 + 尺寸门

**背景**：识别环内白色内容（数字/箭头）时，白色像素若不严格限定在环内，
地形白斑、岩石反光、环外元素都会混进来；曾出现「最大白块」被岩石反光
劫持 > 数字本体、21×21 方窗四角出环、环外箭头被当成环内内容等误判。

**触发场景**：从候选环抠取白色内容做分类时。

**结论**：三层约束——
1. **圆形硬约束**：以盘心为圆心取圆 mask，环外像素一律清零（方窗不行）；
2. **主块取「离盘心最近」**而非「面积最大」：只保留距盘心最近的 ≥3px
   白块，其余丢弃——数字不一定是大块，反光一定不在中心；
3. **内容尺寸门**：真 chevron 20~34px、数字按模板库覆盖的尺寸区间校验。

另有一条用户实测的结构事实：**玩家标记的箭头在环外**（环内是数字就
不该再有箭头身份），环外元素不能参与环内分类。

**适用边界**：适用于「环形标记 + 环内白色内容」的 UI 识别。圆形掩膜
半径、尺寸区间是按实机标定的常量，换游戏/分辨率要重测。

## 4. 模板样本必须实机屏幕口径，且要多尺寸覆盖 + 人工核验

**背景**：早期尝试从 pak 资源解码数字贴图做模板——`mapmarker_02.u`
的解码偏移只有 292 正确，280/288 全是噪声图，且 pak 贴图与屏幕呈现
（抗锯齿、色调映射）不一致；小模板滑窗匹配则「贴哪都高分」（6×3px
模板到处 0.8+），产出 648 个假候选。

**触发场景**：为数字/箭头分类建模板库，或从资源文件提取模板时。

**结论**：
1. 模板一律从**实机帧裁剪**（屏幕口径），不用 pak 解码贴图；
2. 匹配用**归一化 bbox 对齐**（内容框互相拉伸对齐后比 NCC），禁止滑窗；
   加纵横比校验防拉伸蹭分；
3. 每个数字要覆盖**多个尺寸变体**——小路线标记（如 5×8 的"3"）和
   队友大盘（37~90px 的"2"）字形差异极大，只有大盘样本时小字全被
   其他数字模板蹭分（实测小"3"错收 digit1@0.629）；
4. 新增样本**必须放大人工核验**内容确实是什么，绝不能拿当前程序输出
   当答案（否则回归永远 100%，测不出错）。

**适用边界**：所有模板匹配类识别。pak 贴图仅适合取证（读 CDO 常量、
确认资源存在），不适合直接当屏幕模板。

## 5. 双身份节点仲裁：看连线存在性，不看分数

**背景**：节点可能同时有数字身份和箭头身份（数字斜笔画被箭头几何
蹭出假箭头，或反之）。曾按 NCC 分数取高者仲裁，实测翻车：D 点假
chevron 0.713 > 真 bogus 数字 0.602，但用户指出该节点实际由连线决定。

**触发场景**：一个节点同时命中数字与箭头两类身份，需要定它到底是
「方向节点」还是「终点」时。

**结论**：仲裁标准是**箭头指向锥内是否有真实连线**，分数只做辅助：
- 箭头锥内有邻接边 → 它是方向节点，数字身份作废（即使箭头分不高）；
- 锥内无连线 → 数字身份有效，箭头视为蹭分噪声；
- **强数字保护**：数字 NCC≥0.70（实测真数字普遍 0.8+、蹭分 ≤0.6）
  时豁免上述作废，防止真终点被自己的 bogus 箭头杀掉。

**适用边界**：适用于「白块同时可能被多类模板命中」的节点分类。
分数门槛（0.70 强 / 0.55 底线）是 NCC 口径实机标定值，换特征要重标。

## 6. 终点判据用「穿线」，不用箭头锥；折线拐点用邻接方向锥

**背景**：判断链上节点是否为终点时，曾用「入线反方向锥内有无出线」
判定——实测真终点数字的 bogus 箭头（数字斜笔蹭出）可能恰好落在
入线反方向锥内，把真终点误判成中间点；直接延长入线方向判穿线又在
折线拐点（入射 67° / 出线 113°）打偏。

**触发场景**：区分「线穿过中间的标记」与「线到此为止的终点」时。

**结论**：穿线判定改用**邻接方向锥**——存在任一邻接边方向与行进
方向夹角 ≤55° 即判穿线（直线与折线拐点都覆盖），且只用队伍色线掩膜
（细白线单独处理，两掩膜不混用）。线穿过去 → 中间点，数字作废；
线到盘为止 → 数字才轮到当结尾。

**适用边界**：适用于折线/直线混合的路线拓扑。「行进方向」取链上
前一段的方向，单点起链时无行进方向、此判据不适用（靠第 5 条仲裁）。

## 7. 链级方向仲裁：同一路径双向成链时，有箭头驱动者优先

**背景**：放开无箭头起点（第 2 条）后，链可以从任一端反向走通，
同一几何路径产生两条方向相反的链，反向假链（终点挂着弱蹭分数字）
一度反超真链。

**触发场景**：成链不要求全程箭头驱动、允许无箭头链首时。

**结论**：收链时按**路径分组**（同一几何点集 = 一组）做方向仲裁：
组内优先取**有箭头驱动**（链上任一步由箭头锥命中）的链；组内全部
无驱动时取终点数字分最高者。跨路径的同一数字槽竞争：有驱动的链
优先于距离更长的无驱动链。

**适用边界**：与第 2 条配套使用；若某体系链首必有箭头，则不需要
此层仲裁，直接按单向校验成链即可。

## 8. 细线邻接 vs 大盘实心：seg_support 的填充率一刀

**背景**：队友位置大数字盘（37~90px 实心圆盘）之间，队伍色线掩膜
会在盘体内部大面积命中，两点连线采样几乎全程命中——四个队友大盘
互相串成伪边，被当成「有连线」收进假链。

**触发场景**：用「两点间采样命中比例」判定连线存在性，且候选点
可能是实心大盘时。

**结论**：邻接判据区分**细线**与**盘体实心**：每个采样点取 5×5 小框，
框内掩膜填充率 >0.70 判为「这是盘体内部，不是线」不计命中；填充率
0~0.7 才算线经过。这一刀同时杀掉了「大盘群互连」与「线穿过大盘」
两类伪边。

**适用边界**：适用于「细线连接实心标记」的拓扑识别。0.70 阈值按
本机实机帧标定；若标记盘极小（与 5×5 框同量级）需重新标定。

## 9. 小图形的对称分区分度近零：组合判据才是出路

**背景**：几何法箭头上线后，大号数字字形（"1"竖条、"4"斜笔画）
在 ≤90px 小色块上也扫出了 1.0 的对称分（量化噪声在端带退化成
1~2 像素时必然对称），一度到处出假箭头。

**触发场景**：用「对称性」做小尺寸（≤90px）图形的分类特征时。

**结论**：对称分单独使用无区分度（真箭头和数字字形都接近 1.0），
真正起区分作用的是**尺寸门 + 散布对比 + 成链几何裁决**的组合：
尺寸门堵住大数字与碎块，散布比区分 chevron 与近对称数字，残余
假身份由连线存在性（第 5 条）在成链时排除——即「就算数字蹭出
箭头身份，它指向的方向上没有真实连线，自然被排除」。

**适用边界**：普适原则：单一几何特征（对称性/质心/长宽比）在
小图形上都不够，必须多层组合；且识别端不必过度收紧，可以信任
下游拓扑裁决。

## 10. 收链变量 bug：len=1 时 range(0) 为空 → any() 恒 False

**背景**：链级方向仲裁上线后真链全部判成「无箭头驱动」，回归
16/19 卡了三轮；单独验证 `arrow_hit` 却返回 True，行为自相矛盾。

**触发场景**：DFS 收链时计算 `any(箭头命中每一步)` 类的聚合判定。

**结论**：根因是驱动计算误用了外层变量 `path`（应为新路径
`new_path`）：在 len(path)==1 的首步收链时 `range(len(path)-1)`
即 `range(0)` 为空，`any()` 恒 False。修复后回归 19/19。
**方法论教训**：聚合判定结果与单步验证矛盾时，直接 print 聚合
表达式的原始值与类型（`print(repr(x), type(x))`），一轮就能定位；
不要反复重跑同一逻辑寻找「玄学差异」。

**适用边界**：普适 Python 陷阱：`any()`/`all()` 对空可迭代对象
返回 False/True，凡「按步数切片聚合」的写法要先确认步数 >0。

## 11. 回归失败的排查顺序：代码错 or 期望值错，先看图再改码

**背景**：多轮迭代中，回归失败既有代码 bug（drive 变量、掩膜泄漏）、
也有期望值口径问题（槽位按数字 n→槽 n-1 的映射、队友大盘当链首的
真实结构），还有模板覆盖不足（小"3"无样本）。曾因只看程序输出
不看原图，把「链被假链取代」误判成「阈值问题」绕了远路。

**触发场景**：`tools/testset_eval.py` 有用例失败时。

**结论**：排查顺序——
1. **先放大原图人工看**：真实结构是什么（哪个环、什么内容、线连到哪），
   期望值是否成立；用户提供的实机结构描述（如「玩家标记箭头在环外」）
   优先级最高；
2. 再打印节点/身份/邻接/链收集的中间量，与真实结构对照找第一处偏离；
3. 确认是模板/样本覆盖不足时，按第 4 条流程补采（人工核验后入库）；
4. 修完跑回归全过才算完成；临时调试脚本当天清理。

**适用边界**：适用于本项目的回归维护，也适用于任何「识别结果 vs
期望值」对不上的调试场景。核心原则：**看图定真相，程序输出只是
待验证的假设**。

## 12. 开发态回归全过 ≠ 打包态正常：模块私有资源路径必须冻结态感知

**背景**：v8 上线后实机报「无轨迹」，但同一张实机留帧线下复现能正确
认出链路，回归 19/19——开发态与打包态行为分裂。根因：
`marker_detect.py` 用 `__file__/../assets/markers` 拼模板路径。PyInstaller
`--onefile` 下模块被平铺到 `sys._MEIPASS` 根，`__file__/..` 指向解包
目录的**上级**（%TEMP%），`screen_digits/` 目录判定不存在 → 数字模板
全空 → 终点认不出 → 链永远收不了 → `teams: []`。

**触发场景**：任何模块自建资源路径、且该模块是首次（或改动后）进入
打包环境运行时。典型信号：**开发态正常、EXE 里功能静默缺失**（本例
模板加载失败只是 `os.path.isdir` 为 False，无报错、无日志）。

**结论**：
1. 模块内资源路径一律做冻结态感知：
   `sys.frozen` 时用 `os.path.join(sys._MEIPASS, 'assets', ...)`，
   开发态才用 `__file__` 相对拼接（`main.py` 的 `app_root()` 是现成
   范式；不能 import main 时就地复制这套判断）；
2. 打包后首次运行要做**冒烟验证**——EXE 环境里跑一遍带资源依赖的
   功能（或至少确认模板文件存在于 `_MEIPASS/assets/...`），
   不能只信开发态回归；
3. 排查此类问题的第一步：对比「同一帧线下结果」与「EXE 日志结果」，
   分裂即锁定打包环境差异，而不是继续调算法。

**适用边界**：所有 PyInstaller 打包的 Python 项目。注意静默降级陷阱：
`os.path.isdir()` / `os.path.exists()` 判 False 后走空分支不报错，
这类失效在 EXE 里完全不可见，务必让资源加载失败至少打一条日志。
